Mail-agent benchmark: app map

A take-home guide to where things live and where to start a change.

What it is

A local benchmark for an email assistant. It runs any system that honours its trace contract through 20 fictional university scenarios (replies, new mails, summaries, missing mail, injected instructions). It scores each scenario layer by layer (route, tools, facts, output) to debug one system, and on an outcome-only scorecard with 9 dimensions to compare different systems. A llama3.1:8b judge grades tone, relevance and conciseness. Hand-written good and broken reference traces prove that every check works.

  • Mailbox server: a fictional mailbox over MCP (stdio), with no send tool. It logs every tool call.
  • Runner: starts the system once per scenario and hands it the mailbox.
  • Checks and judge: score the trace and the mailbox log against the scenario's answer key.
  • Run store: every run is saved as benchmark/runs/<timestamp>/results.json for comparison.

One action, end to end: ./bench run --system "…" --repeat 3

Reference route: three stops

Paths are relative to benchmark/src/main/java/com/assistant/mail/bench/. Search for the anchor text in your editor.

  1. The trace contract in action, Bench.java, anchor static String runSystem(.
    This is where the system gets started with sh -c and the three environment variables, with the 5-minute timeout. A non-zero exit or a missing trace comes back as the reason for invalid. This is the only place that knows how a system is launched.
  2. Outcome-only scoring, Checks.java, anchor static ObjectNode dims(.
    It reads only the drafts in the mailbox log and the output step: task, factuality, conciseness for summaries, and injection. Judge.java → void apply( then adds tone, relevance and concise. The per-layer diagnosis is in static ObjectNode score(, just above.
  3. From results to a number, Bench.java, anchor static ObjectNode scorecard(.
    It turns each execution's dimensions into 0–1 rates, adds reliability, consistency across repeats and latency 1 / (1 + p95 / 60 s), and averages them into the composite. static int compare( and static void printScorecards( print two runs side by side.

A practice to reuse

Test the evaluator before trusting it. In this benchmark, every check is proven by references whose outcome is known in advance. Good references must pass, and each broken reference must fail at exactly its layer (./bench check, 143 references). This caught real grader bugs:

  • vous matched inside "Rendez-vous" (too strict).
  • A 15:30:00Z timestamp made an invented "30" look grounded (too loose).
  • A correct question in no-match-02 was scored by a summary's length rule.

The judge reached 0 disagreements only after four calibration rounds. The same move works for any test suite, metric or LLM grader: feed it outputs you already know are right and wrong, and check that it agrees before you use it to judge a system.
