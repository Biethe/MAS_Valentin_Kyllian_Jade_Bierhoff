My Mail Agent

Four pieces on your machine: a fictional university mailbox served over MCP, your agent pipeline on a local model, a tracer that writes down every step, and a benchmark that checks every layer and compares runs.

How the pieces connect

One run, step by step

How you run it

# prerequisites: Java 21, Maven, ollama serve, qwen3.5:4b + llama3.1:8b pulled
mvn -q package      # compile + copy dependencies to target/lib
./bench run         # every scenario → global verdict
./bench diff        # per-component flips vs previous run
./bench show <id>   # one scenario's trace, step by step

Components

Mailbox Server

A local MCP server over stdio, holding one scenario's simulated mailbox. Tools: search_mail, read_mail, read_thread, create_draft. There's no send tool, so the server itself enforces draft-only.

MCP Mail Client

Implements MailClientMcp plus createDraft over stdio. Every call is traced. The real Gmail and Outlook MCPs plug in here later.

service/mcp/prd › Tracing
Ollama Client

POST /api/chat with temperature 0 and seed 42, using the JDK HttpClient. Each call is traced, and the model digests are recorded per run.

service/llm/OllamaClient.java
Agents

Your planner, drafter and summarizer, backed by Ollama. Adds block parsers (a parse failure makes the scenario invalid), the language rule, and a SUSPICIOUS_INSTRUCTION kind for injections. The validator isn't wired into this slice.

service/agent/prompt/prd › Languageprd › Injected Instructions
Pipeline

Routes each atomic instruction. REPLY and COMPOSE go to the draft workflow, SUMMARIZE to the summary workflow, and anything unclear or without a match goes to the ask-user path, which ends the scenario. The code makes the tool calls.

workflow/prd › The Core Journeyprd › Missing Information
Tracer

One JSON line per step, tagged by layer: route, tool, facts, output, ask, judge.

trace/Tracer.javaprd › Tracing
Scenario Set

A fictional university (people and roles), tone profiles, and 10 scenarios (2 per kind) in French and English, each with a per-layer answer key.

scenarios/prd › Scenariosprd › Tone Profiles
Layer Checks

Plain-code checks in order:

  • Route: instruction types and the clear flag.
  • Tool calls: required reads, draft fields, forbidden arguments.
  • Facts: regex patterns, plus injection tagging.
  • Output: required and forbidden patterns, greeting, language (stopword ratio), invented emails, dates and numbers, and the 50% word ratio for summaries.

Every layer is computed; the outcome uses the first one that fails.

bench/Checks.javaChecksTest.javaprd › Run Outcomesprd › Output Check: Summaries
LLM Judge

Runs on llama3.1:8b (bigger, open weights, fast and non-reasoning, a different family from the agents), in its own pass after all scenarios so only one model sits on the 8 GB GPU at a time. One criterion per call, answering pass or fail plus a reason. Verdicts are cached by a hash of the output, and an unreadable answer is counted as a judge error, separate from a system failure.

bench/Judge.javaprd › Output Check: Replies and New Mails
Runner and Report

A preflight checks Ollama and both models before anything runs. Each scenario has a 5-minute timeout. The verdict compares successful-scenario counts, with per-layer passes as tie-breakers; the first run is the baseline. Runs with different setups print "not comparable" instead of a verdict.

Where data lives

In git

  • scenarios/*.json: mailbox, request, answer key per layer.
  • university.json, tone-profiles.json: people, roles, default tones.

Local, gitignored

  • runs/<time>/results.json: setup, outcome, and every layer per scenario.
  • runs/<time>/traces/*.jsonl: every step.
  • runs/judge-cache.json: cached verdicts.

Decisions and open issues

Your decisions

  • Code-driven tool calls: may revisit.
  • A local MCP server for the fictional mailbox.
  • A judge from a different model family, French and English: llama3.1:8b in a separate judging pass.
  • Reply in the received language; new mail in the user's language, default French.
  • Draft, never send.
  • A UI goes to Later.

Simplified on purpose

  • Simulated mailbox instead of live mail.
  • The ask-user path ends the scenario.
  • Pattern-based fact checks and an entity-based hallucination check.
  • Stopword-ratio language check.
  • 10 scenarios.
The useful unknown

Can an LLM judge be stable? Yes, with pass/fail verdicts, temperature 0 and a seed, cached verdicts, and recorded setups. But stable isn't the same as correct. After the first run, hand-check the judge on the writing scenarios, and swap the model or prompt if you disagree with more than one or two.
