My Mail Agent

A traceable, benchmarked local multi-agent mail assistant for a university. The benchmark comes first, so every change answers “is the system getting better?”

The kernel

A fictional university is the ground truth. Every scenario defines the expected behavior at each layer, not only the final email. Each decision is traced and scored on its own, and the whole run is scored end to end.

Who it's for

Now

The learner, as the developer iterating on the system. They need to see which decision at which layer got better or worse after each change.

Eventually

Someone at a university dealing with “tons and tons of emails”: a professor, researcher, student or administrator. They need replies, new mails and summaries in the right tone for each recipient, without their mail leaving their machine.

What “working” looks like

“When I can trace every single decision, you know, input output that happens in my system. I can trace it, I can evaluate it. So I can tell if that is good or bad.”

The proof moment: a scenario fails, and the trace points to the exact layer and decision that went wrong instead of only showing a bad final email.

Component map

Later 5

Central deployment

A university-hosted server for many trusted users, including tenant isolation: user A's mail must never reach user B. “Requires more thinking and more time… a layer of complexity I haven't really thought through.”

Critic agent

Replaces the current validator and loops feedback to the planner, summarizer and writer.

Deterministic tool-call validator

No LLM. Checks format (JSON/XML), parameter count and schema on every MCP call, at runtime too.

Memory component

Not thought through yet, and it will need its own evaluation.

Research map

AgentDojo

Email, calendar and cloud workspace, with prompt injections placed inside email bodies. Success is checked by deterministic functions over the final environment state.

WorkBench

Simulated email, calendar and other databases. A task is graded by comparing the final state against the expected one, with no LLM judge.

Berkeley Function Calling Leaderboard

Checks tool calls by matching their structure (AST). Close to the deterministic tool-call validator idea.

Why it matters

“A very strong agentic system, with deterministic or evaluatable behavior and outcomes… every time I do something… check, am I going in a good direction… is the system getting better?”

The project started with one of the learner's professors. The learning goal is how to evaluate an agent system.

Open questions for the PRD and spec

  1. How the fictional university's mailbox reaches the agents in a reproducible run, given that live Gmail or Outlook isn't static. A simulated mail MCP seems implied.
  2. How to evaluate the whole system: “I'll have to find out a way.”
  3. How to grade open-ended outputs such as reply quality and tone objectively.
  4. Whether prompt-injection scenarios are in the first scenario set.
  5. Whose agent each scenario runs as, meaning which role owns the local agent.
  6. How to keep scores comparable when a local model isn't fully deterministic.
