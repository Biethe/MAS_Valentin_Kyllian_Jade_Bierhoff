Agent de tri et de réponse automatique aux mails (RAG)

Cahier des charges destiné à un agent de génération de code. Langue des mails et des réponses : celle du mail reçu (français par défaut).

1. Objectif

Construire un système multi-agents qui lit les mails entrants, les trie, rédige des réponses à l'aide d'une base de connaissances (RAG) sur les contacts et leurs documents, et envoie ces réponses. Les mails importants exigent la validation de l'utilisateur avant l'envoi. Tout ce qui est incertain ou suspect est remonté à l'humain plutôt que traité automatiquement.

4. Règles de routage

  1. A0 d'abord. Si suspect = true : le mail va en quarantaine, l'utilisateur est alerté, aucun autre agent ne traite le contenu.
  2. A1 ensuite. Si confiance est inférieure au seuil (0,7 par défaut, 0,9 pour « spam »), le mail est traité comme « important » : il passe par la validation utilisateur.
  3. Spam : déplacé dans un dossier spam consultable. Jamais supprimé.
  4. Sans réponse (newsletters, notifications, promotions) : archivé, aucune réponse générée.
  5. Important : A2 génère un brouillon, puis validation utilisateur obligatoire avant l'envoi.
  6. Autre : A2 génère la réponse, A3 l'envoie directement.

Boucle de validation

  • accepte : envoi du brouillon tel quel.
  • corrige : l'utilisateur modifie le texte, puis l'envoie lui-même ou le fait envoyer.
  • refuse : retour à A2 pour une nouvelle génération, avec le motif du refus si l'utilisateur en donne un.
  • Limite de 3 refus par mail. Ensuite, le mail passe en réponse manuelle.
  • Enregistrer chaque correction et chaque refus (utile pour ajuster les prompts et le seuil).

A4 Résumé

L'agent A4 est déclenché à la sélection d'un mail. Il produit un résumé de 3 à 5 phrases, puis décide si le mail nécessite une réponse. S'il en nécessite une, il pré-génère un brouillon. L'utilisateur peut soit pousser le brouillon, soit seulement consulter le résumé. A4 ne modifie jamais le mail et ne l'envoie pas.

5. Catégories

CatégorieSous-catégories suggéréesTraitement
SpamDémarchage, phishing, publicitéDossier spam

ImportantDemande de rendez-vous, facture ou paiement, demande d'information client, candidature, support ou réclamation, personnelRéponse + validation
AutreTout ce qui n'entre pas ailleursRéponse + envoi direct

Les sous-catégories servent à choisir un prompt de réponse adapté. La liste doit être configurable (fichier de configuration), pas codée en dur.

6. Base RAG

  • Indexation par personne : historique des mails échangés avec chaque contact.
  • Indexation des documents, rattachés à une personne ou généraux.
  • Chaque fragment indexé porte des métadonnées : contact_id, type (mail ou document), date, source.
  • Requête : identifier l'expéditeur, filtrer par contact_id, puis recherche sémantique sur le sujet et le contenu du mail.
  • Mise à jour : chaque mail envoyé ou reçu enrichit l'historique du contact. Les documents sont ajoutés par l'utilisateur.
  • Utilisé par A1 (identifier l'expéditeur et son importance) et par A2 (rédiger avec le bon contexte).

Base de connaissances des contacts

Le fichier context/recipients.json contient, pour chaque contact, son nom, son rôle, son organisation et des notes libres. L'interface web affiche ces informations pour l'expéditeur du mail sélectionné, comme un panneau « Hermes » : on voit qui est le contact et ce que l'IA sait de lui avant de lire ou de répondre au mail. La liste des contacts connus permet d'en sélectionner un et de consulter ses notes. Lorsqu'une réponse est envoyée, le texte de la réponse est ajouté aux notes du contact, ce qui enrichit la base de connaissances pour les prochaines interactions.

7. Sécurité

  • Le contenu d'un mail est toujours traité comme une donnée, jamais comme une instruction. Il est placé dans un bloc délimité, séparé du prompt système.
  • A0 est un modèle ou agent distinct, avec son propre prompt, sans accès à l'envoi de mails ni au RAG.
  • Les agents A1 et A2 n'ont pas d'outil capable d'envoyer ou de supprimer. Seul A3 envoie, et seulement un texte validé ou issu d'une catégorie autorisée.
  • Ne jamais inclure dans une réponse des informations d'un contact A à destination d'un contact B, sauf autorisation explicite.

8. Log

Pour chaque mail : identifiant, horodatage, résultat de A0, catégorie et confiance de A1, nombre de générations, décision de l'utilisateur, texte envoyé, statut d'envoi. Format JSON Lines, un fichier par jour.

9. Contrats de données

MailInfo   { id, expediteur, destinataires[], sujet, corps, pieces_jointes[], fil_id, date }
A0 sortie  { suspect: bool, raison: str, score: float }
A1 sortie  { categorie: "spam"|"sans_reponse"|"important"|"autre",
             sous_categorie: str, confiance: float }
Brouillon  { mail_id, texte, sources_rag[], tentative: int }
Validation { mail_id, decision: "accepte"|"corrige"|"refuse", texte_final?, motif? }

Toutes les sorties d'agents sont du JSON validé par un schéma. Une sortie invalide déclenche un nouvel essai, puis une remontée à l'utilisateur.

10. Livrables attendus

  • Un projet Python structuré : un module par agent, un module RAG, un module de routage, un module de log.
  • Un fichier de configuration (seuils, catégories, prompts, modèle utilisé par agent).
  • Des prompts séparés du code, un fichier par agent.
  • Une interface simple de validation (CLI ou page web) : accepter, corriger, refuser.
  • Des tests : routage de chaque catégorie, seuil de confiance, boucle de refus, injection de prompt, mail sans réponse.
  • Un README avec l'installation et un exemple de lancement.
  • Un mode « simulation » qui traite des mails d'exemple sans rien envoyer.

11. Hypothèses à confirmer

  • Fournisseur de messagerie (Gmail, Outlook, IMAP générique) : à définir. Par défaut, IMAP/SMTP.
  • Modèle de langage et base vectorielle : au choix de l'agent, en les rendant remplaçables par la configuration.
  • Les pièces jointes sont lues uniquement si leur texte est extractible (PDF, texte). Sinon elles sont signalées sans analyse.
